Stress test: a realistic dense multi-select question. 70-word prompt with embedded math. Five choices ranging from 9 words to 33 words; some wrap to 4 lines at narrow. Free-form has a multi-line placeholder. This is the kind of question that would surface in a graduate-level chain-rule lesson, a textbook problem disambiguation, or a course-create draft review.

What holds up:
  • Wide: prompt and choices read cleanly; the 3 selected badge sits naturally between Submit and clarify-in-chat. Each choice is 1-2 lines.
  • Medium: tighter padding (from @container chat (max-width: 599px)) pulls the card inward; choices grow to 2-3 lines but the radio/check indicator stays anchored top-left. Free-form text area scales to width.
  • Narrow: action row stacks vertically per container query — Submit, the badge, and clarify each get their own row, full width. Choices wrap to 3-4 lines; the prompt is the densest block. Layout doesn't break.
Where it strains:
  • At narrow the long prompt + 5 multi-line choices push the card past 700px tall — significant scroll. Two cards in a paged set would make the chat surface feel overwhelmed.
  • The 3 selected badge currently sits in the action row; at narrow it wraps below the primary Submit. Visual is acceptable but feels slightly orphaned. Worth considering whether the selected count belongs in the kicker (top) instead of the actions row (bottom).
  • Math notation (e2x, etc.) isn't rendered via KaTeX in mocks — production would be richer; the wrap behavior is broadly representative but exact heights will differ.
Tool-schema constraints worth adding (input to feature-question-panel-rework design):
  • Prompt max ~50 words (~300 chars). Beyond this, the tutor should issue an explanatory chat turn before the question card, not stuff context into the prompt itself.
  • Per-choice max ~15 words (~80 chars). Choices longer than this read like they should be paragraphs, not options — surface the long content in the chat turn, keep choices crisp.
  • Choice count cap: 5 (we already have this implicitly via Miller's 7±2, but worth explicit in the schema).
  • Multi-select hard cap: 6 choices; beyond that, single-select with a refining follow-up is the right shape — multi-select fatigue is real.
These caps should be enforced in the ask_student_question Zod schema with descriptive error messages so the agent learns the constraints by reading them, not by repeated rejections.
