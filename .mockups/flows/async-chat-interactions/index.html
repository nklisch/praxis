flow · async chat interactions

How click should feel, after the audit

Five interactive scenarios demonstrating the optimistic-dispatch + async-error pattern that feature-refactor-async-chat-interactions-audit will establish across every UI surface that triggers engine work. Each page is clickable — the timing is simulated, but the behavior is faithful.

canonical pattern

Click fires the action. The originating affordance commits immediately — it does not disable, dim, or change shape. A subtle pending pip appears beside it. If the engine returns success, the pip vanishes and the result lands wherever it lands. If it fails, the pip turns into a warning glyph; one click retries with the same params. If the failure goes unattended, the activity strip picks it up as a persistent banner.

Composer · send while tutor streams

Type and send a follow-up while the tutor is mid-response. The message queues inline as a ghost bubble; the Send button is now Stop. Try editing or removing a queued message before it dispatches.

Pick an answer, hit Submit. The card collapses to a chip the moment you click — no greyed-out wait through the round-trip. The tutor's next turn starts streaming behind it.

"Materialize" button · pending pip → result lands

An in-chat button that fires an engine job. Click it: the button doesn't disable, a tiny pip appears beside it, and the result eventually arrives in the thread.

4

Failed dispatch · inline ⚠ → one-click retry

Same affordance as scenario 3, but the engine fails. Pip turns to ⚠. Click the warning to retry — params were captured at dispatch, no re-input needed.

→
5

Escalation to the activity strip

A failure goes unaddressed for ~30s. The activity strip at the top of the workspace lights up with the failed item, surfacing it persistently. Two-tier so transient failures don't pollute the strip but lingering ones can't be missed.
