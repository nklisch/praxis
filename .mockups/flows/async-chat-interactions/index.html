flow · async chat interactions

How click should feel, after the audit

Five interactive scenarios demonstrating the optimistic-dispatch + async-error pattern that feature-refactor-async-chat-interactions-audit will establish across every UI surface that triggers engine work. Topology: hybrid — walk sequentially via prev/next, or jump to any scenario. Each page is clickable; timing is simulated, behavior is faithful.

canonical pattern

Click fires the action. The originating affordance commits immediately — it does not disable, dim, or change shape. A subtle .action-pip appears beside it. If the engine returns success, the pip vanishes and the result lands wherever it lands. If it fails, the pip turns into ⚠; one click reveals a .failure-popover with retry that uses the same dispatch params. If the failure goes unattended for ~30s, the .status-strip picks it up as a persistent banner.

hybrid topology — sequential walk + cross-jumps
1

Composer · send while tutor streams

Type and send a follow-up while the tutor is mid-response. Queues inline as a ghost .chat-turn--queued; Send becomes Stop in place via .composer__send--stop; per-bubble edit/remove before dispatch.

→
2

Structured question · single + multi-select, submit dismisses immediately

Pick an answer, hit Submit. The .inline-question collapses to a .thread-chip the moment you click — no greyed-out wait. Two questions in this scenario: single-select (radio) and multi-select (checkbox + "select all that apply"). Try clarify in chat on the other.

→
3

Action card · "Save as flashcards" → pending pip → result lands

The user-initiated commit pattern. The tutor has already produced four practice items; the .action-card offers to materialize them as flashcards in the user's deck. Click commits via .action-pip--pending. Result lands as a confirmation card in the thread. The action button never disables.

→
4

Failed dispatch · inline ⚠ → one-click retry

Same affordance as scenario 3, but the engine fails. Pip turns to .action-pip--failed; click opens a .failure-popover with retry. Retry uses the params captured at click-time — no re-input needed.

→
5

Escalation to the activity strip

A failure goes unaddressed for ~6s (compressed from production's 30s). The .status-strip--active slides down with the failed item as a persistent banner. Tier 1 (inline) and tier 2 (strip) coexist; resolving either clears that tier independently.

→

Components composed (see .mockups/design-system/components.css)

  • .chat-surface + --wide / --medium / --narrow — container-aware chat host; @container queries adapt children
  • .chat-turn family — --tutor / --student / --queued / --failed + __streaming / __badge / __position / __actions
  • .composer + .composer__send--stop modifier · .composer__status + --streaming / --failed · .composer__hints--split
  • .inline-question + __choice + __indicator--radio / __indicator--check + __free-form + --bare + --dismissed
  • .inline-question-set + __head · uses existing .tabs + .tab for paging
  • .thread-chip + --dismissed · resolved-question summary in chat history
  • .action-card + __body + __action · canonical in-chat user-initiated affordance
  • .action-pip + --pending / --success / --failed / --retrying · no squash/overshoot per locked motion attitude
  • .failure-popover + __label / __reason / __actions · anchored to .action-card__action
  • .status-strip + --active · escalation tier (mirrors production <StatusStrip>)
