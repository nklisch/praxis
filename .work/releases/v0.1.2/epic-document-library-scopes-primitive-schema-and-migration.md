# Schema + migration: `document_scopes` table

## Scope

Land the schema change and the Drizzle migration that moves
`course_documents` data into the new `document_scopes` table. Pure DB
work — no service or call-site changes yet. The schema change leaves
the consuming service file (`course-documents-service.ts`) referencing
a now-deleted export, which `pnpm typecheck` will flag; that's expected
and gets fixed in the next story.

This is the foundation story — the next two stories build on it.

## Units in this story

- Unit 1 (schema change in `packages/artifacts/src/schema.ts`)
- Unit 2 (Drizzle migration SQL with data-copy + drop)

## Acceptance Criteria

- [ ] `courseDocuments` export removed from
      `packages/artifacts/src/schema.ts`; `documentScopes` export
      present per the design.
- [ ] New migration file in `drizzle/` (next sequence number, likely
      `0014_*.sql`) generated via `pnpm db:generate` and hand-edited to

      TABLE course_documents` steps.
- [ ] `drizzle/meta/_journal.json` updated by `db:generate` (auto).
- [ ] `pnpm db:reset` runs cleanly on a fresh DB.
- [ ] (Manual) On a populated dev DB, the migration preserves every
      `course_documents` row as a `document_scopes` row with
      `scope_kind='course'`.

## Implementation Notes

### Files changed

- `packages/artifacts/src/schema.ts` — replaced `courseDocuments` export
  with `documentScopes`; updated `artifactsSchema` aggregate export to
  reference `documentScopes` instead of `courseDocuments`; removed the
  `Phase 16: Course ↔ Document attachment` comment header.
- `drizzle/0014_document_scopes_migration.sql` — hand-written migration
  (see note below on `--custom` approach).
- `drizzle/meta/_journal.json` — added idx 14 entry for
  `0014_document_scopes_migration` with `when: 1778639734837`.
- `drizzle/meta/0014_snapshot.json` — generated by `drizzle-kit generate
  --custom`, then updated via Python script to replace `course_documents`
  table with `document_scopes` in the snapshot tables map.

### Migration approach deviation

`pnpm db:generate` was initially attempted to auto-generate the schema
diff, but Drizzle (in non-TTY mode) fails with an interactive prompt when
it detects a possible table rename (`course_documents` → `document_scopes`).
Used `drizzle-kit generate --custom --name document_scopes_migration`
instead to create the journal entry and snapshot skeleton, then:

1. Manually wrote the full SQL migration in
   `drizzle/0014_document_scopes_migration.sql` (CREATE TABLE, indexes,
   INSERT…SELECT, DROP TABLE — matching exactly what the auto-diff would
   have produced plus the data-copy step).
2. Updated `0014_snapshot.json` to replace the `course_documents` table
   definition with `document_scopes` so future `db:generate` calls diff
   correctly from this snapshot.
3. Manually added the `0014_document_scopes_migration` journal entry to
   `_journal.json` (the `--custom` flag had previously added it, but it
   was lost due to a file revert mid-session; re-added it by editing the
   file directly).

### Verification

`pnpm db:reset` completes cleanly. Post-reset:
- `document_scopes` table present with correct composite PK, FK cascade,
  and two indexes.
- `course_documents` table absent.
- `__drizzle_migrations` has 15 rows (0000–0014); last timestamp
  `1778639734837` matches the 0014 journal entry.

### Expected typecheck failure

`pnpm typecheck` will fail because `course-documents-service.ts` and
other consumers still reference the now-deleted `courseDocuments` export.
This is intentional per the story scope — fixed in
`epic-document-library-scopes-primitive-service-and-types`.

**Notes**:
- Schema shape matches design exactly: composite PK on `(document_id, scope_kind, scope_id)`, FK cascade on `document_id`, two indexes (scope-idx on `(scope_kind, scope_id)`, document-idx on `document_id`), `scope_kind` enum `["course","session"]`, `source` enum `["bootstrap","manual","ingestion"]`.
- Migration is ordered correctly (CREATE → INSERT…SELECT → DROP), uses Drizzle's `--> statement-breakpoint` convention, and runs in better-sqlite3's default transaction so a mid-migration failure rolls back.
- The `--custom` workaround for non-TTY `db:generate` is documented in implementation notes; the resulting SQL matches what an auto-diff would produce plus the data-copy step.
- Foundation doc roll-forward: `docs/ARCHITECTURE.md:388-390` already references the `document_scopes` polymorphic table — drift-free.
- Expected typecheck failure (call sites still reference removed `courseDocuments`) is documented and resolved in the next story.
